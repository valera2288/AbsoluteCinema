## 1. Основание и устройство приложения

Функции и условия приёмки задаёт [ТЗ](<Приложение А. Техническое задание — Онлайн-кинотеатр.docx>). Порядок реализации и дополнительные правила операций задаёт [план разработки](<План разработки.md>). Роли, функции и исходные сущности сверены с [диаграммой вариантов использования](online_cinema_use_case.drawio), [функциональной схемой](online_cinema_functional_scheme.drawio) и обеими страницами [ER-модели](online_cinema_ER.drawio). На момент проектирования в папке есть исходные документы. Исходного кода, миграций и предыдущей архитектуры нет. Расхождения с практическими последствиями перечислены в [разделе 11](#11-расхождения-риски-и-открытые-вопросы).

**Стек разработки и учебного стенда** — Python 3.13, Django 5.2 LTS, PostgreSQL 17 и psycopg 3.2. Локальные исполняемые файлы сообщают Python 3.13.3 и PostgreSQL 17.6. Установить поддерживаемые патч-версии выбранных веток, проверить запуск и миграции на чистой PostgreSQL, затем закрепить версии Python-пакетов в `requirements.txt`. По п. 4.5.3 ТЗ нужны также Pillow для изображений и openpyxl для XLSX. Официальные справочники для сверки на этапе 1 — [поддержка Python в Django 5.2](https://docs.djangoproject.com/en/5.2/faq/install/#what-python-version-can-i-use-with-django) и [требования Django 5.2 к PostgreSQL и драйверу](https://docs.djangoproject.com/en/5.2/ref/databases/#postgresql-notes). В этой работе доступ к этим страницам через Firefox остановило ограничение Computer Use. Совместный запуск предстоит проверить при создании проекта.

Один Django-проект формирует HTML по схеме MVT. Django ORM обращается к PostgreSQL. JavaScript управляет плеером, состоянием мобильных фильтров и подтверждениями, а также отправляет прогресс и запросы активности. Файлы остаются на диске. Локальный имитатор оплаты — модуль Django, тестовая почта — файловый почтовый backend Django. Рекомендации вычисляются запросом по данным профиля. Для учебного стенда достаточно этих компонентов и команд Django, запускаемых оператором.

Координация удаления аккаунта, отзыва устройств и блокировки находится в `config/workflows.py`, где можно вызвать сервисы нескольких областей без встречных импортов между их моделями. | Подписчик | Дополнительно плеер, продолжение просмотра, разрешённое скачивание и рекомендации. Право определяется при каждом защищённом запросе по действующему периоду. |
| Модератор | Собственная очередь `/moderation/reviews/` с фильтрами по статусу и датам, по умолчанию «На модерации», старые поступления первыми. Видит дату, публичное имя профиля, оценку, текст и статус. Может опубликовать, отклонить, снять с публикации и переключить право автора на текстовые отзывы. Действия требуют отдельных разрешений. |
| Администратор | Django Admin для фильмов, жанров, медиа, тарифов и промокодов. Отдельные формы или действия внутри Admin для публикации, ролей, блокировки, удаления аккаунта и возврата. Подписки и платежи доступны для просмотра. Для обращений, рассылок, журнала, отчётов и копирования нужны специализированные представления внутри Admin. |

Служебные полномочия хранятся в Django Groups и permissions. `is_staff` открывает вход в Django Admin, `is_active` определяет возможность входа в аккаунт. Модератору достаточно разрешений своей очереди. Администратор стенда получает нужные разрешения своей группы. Внешние запросы меняют данные через POST с CSRF, сервер проверяет пользователя, разрешение и владение объектом независимо от наличия кнопок на экране. Формы сохраняют безопасные поля и показывают причины отказа. Cookie Django защищены `HttpOnly` и `SameSite=Lax`, на сетевом стенде также `Secure` и HTTPS. Тексты выводятся с экранированием, запросы идут через ORM или с параметрами, секреты задаются окружением. Служебные статусы меняются через сервисы, включая Django Admin.

### Общее правило записи

Любая операция, затрагивающая доступ аккаунта, выполняется в `transaction.atomic()` с `select_for_update()` на строке этого `User`. Это относится к профилям и PIN, подпискам и платежам, отзыву устройств, записи прогресса, блокировке и удалению. Под блокировкой данные и время считываются заново. Если нужно заблокировать несколько аккаунтов, их строки берутся по возрастанию PK, до фильма или обращения. Дальше сервис блокирует или изменяет зависимые записи, если этого требует операция. Изменение доступности фильма сериализуется для операций публикации и загрузки на строке фильма. Когда операция требует обе блокировки, сначала блокируется аккаунт, затем фильм. Длительное чтение файла и отправка почты выполняются за пределами транзакции. Уведомление в кабинете и обязательная запись аудита создаются в транзакции породившего их действия. Ошибки файловой системы и имитатора обрабатываются с безопасным кодом причины и без личных сведений в техническом логе.

## 2. Модели и ограничения PostgreSQL

Имена классов и таблиц ниже задают основу миграций. PK по умолчанию — `BigAutoField`. Операционные даты хранятся как `DateTimeField` с часовым поясом, `USE_TZ=True`. Бизнес-периоды полуоткрытые `[start_at, end_at)`. При фильтрации отчётных дат и проверке календарных дат промокодов используется `Europe/Moscow`. День тарифа — 24 часа. Цена хранится в `Decimal(10, 2)` в рублях. `FK` обязателен, кроме полей с `NULL`. В колонке «Связи» указано действие Django при удалении цели FK. FK индексируется по умолчанию, уникальное ограничение уже даёт индекс. В последней колонке перечислены дополнительные индексы под запросы приложения.

| `operations.AuditEntry` → `audit_log`, ТЗ/план | `action`, `object_kind`, безопасный `object_ref`, `result_code`, `created_at`, `event_key`. | `actor` и при наличии `subject_user` NULL, SET_NULL. | `event_key` уникален для логической операции. `(action, -created_at)` для журнала. |
| `operations.BackupRun` → `backup_runs`, ТЗ 4.1.13 | Результат запуска копирования. `started_at`, `finished_at`, `status`, `archive_name`, безопасный код ошибки. | `requested_by` NULL, SET_NULL. | Уникальное имя архива, `(-started_at)` для списка запусков. |

Временные файлы, способы оплаты и служебные записи появляются вместе со своими сценариями. Для удаления профилей, смены роли, публикации фильма, изменения статусов подписки и плеера прямые массовые изменения в Admin закрыты. Ограничения между несколькими строками проверяют операции под блокировкой. `CHECK` не подменяет проверку владения и переходов статусов.


## 3. Аккаунты, профили и устройства

1. **Регистрация.** `AUTH_USER_MODEL = "accounts.User"` до первой миграции. Основа — `AbstractUser` без поля `username`, с `USERNAME_FIELD = "login"`, собственным manager, формами и настройкой Admin. У `login` есть обычный `unique=True` для контракта Django и ограничение `Lower(login)` для регистра. Оба обязательных ограничения `Lower` задаются с именами из плана. Логин начинается с латинской буквы и содержит 4–30 символов из латинских букв, цифр и подчёркивания. Email до 254 символов. Пробелы по краям логина и почты убираются, регистр нормализуется одинаково при записи и поиске. Пароль 8–64 символа, в нём есть буква и цифра, подтверждение совпадает. Django хранит солёный PBKDF2-хеш. При конфликте уникальности после параллельной записи сервис откатывает создание аккаунта и профиля и возвращает ошибку соответствующего поля. Первый профиль взрослый. После регистрации открывается вход. Телефон в кабинете необязателен, при заполнении допускает 10–15 цифр и начальный «+».
2. **Вход и восстановление.** Backend ищет логин или email регистронезависимо. Неверному паролю, неизвестному и заблокированному аккаунтам соответствует общее сообщение. Для пары «нормализованный идентификатор и IP» после пяти ошибок в скользящем окне 15 минут ставится блокировка на 15 минут. Дополнительно ограничить IP до 30 запросов входа за 15 минут, включая обращения с разными идентификаторами. Для обоих счётчиков хранится ограниченный список времён в PostgreSQL. Строки лимитов создаются с опорой на уникальность и обрабатываются под блокировкой в порядке IP → пара. Успешный вход очищает ошибки пары. IP берётся из доверенного источника запроса. Одноразовый сброс использует токен Django и `PASSWORD_RESET_TIMEOUT = 1800`. Под блокировкой повторно проверить токен, записать новый хеш и отозвать все устройства и плееры. Второй параллельный POST видит использованный токен. Ответ на запрос ссылки одинаков для любого email, а истёкшая или использованная ссылка предлагает запросить новую. Смена пароля из кабинета и удаление аккаунта требуют текущий пароль.
3. **Профили.** Первый в порядке создания профиль выбирается при новом входе. Его можно удалить, если останется хотя бы один. Добавление, удаление и переключение выполняются под блокировкой аккаунта. Устройство хранит выбранный профиль и отдельно исходный защищённый профиль. При входе в детский профиль с включённым контролем сервер устанавливает `kids_locked` и сохраняет его в `guarded_profile`. Переход между детскими профилями сохраняет исходную привязку, даже если у нового профиля нет PIN. Если PIN включили на уже открытом детском профиле, сервер устанавливает защиту на устройствах с этим активным профилем, сохраняя ранее установленную исходную привязку. После удаления активного профиля требуется снова выбрать доступный профиль. Сервер применяет возрастной предел 12+ к главной, выборке каталога, прямому адресу карточки, медиа, истории и рекомендациям для детского профиля. На взрослом профиле действуют общие правила каталога. При переключении профиля или включении детского режима ранее выданные сеансы затронутых устройств закрываются. Изменения профилей, которыми можно снять активный детский режим, проходят ту же проверку PIN, включая удаление текущего детского профиля и снятие его детского признака. При удалении исходного защищённого профиля `guarded_profile` обнуляется, а `kids_locked` остаётся. Если исходный профиль удалён или его PIN отключён, выйти из защищённого контекста может владелец по текущему паролю аккаунта. Хеш удалённого профиля не сохраняется.
4. **PIN.** Четырёхзначный PIN хранится в `Profile.pin_hash` как солёный PBKDF2-хеш. Установка, смена и отключение контроля выбранного профиля требуют текущий пароль владельца. При выходе из защищённого детского режима или выборе взрослого профиля сервер проверяет PIN из `guarded_profile`. Текущий детский профиль может отличаться от исходного. После успешной проверки сервер снимает старую защиту устройства и устанавливает новую, если выбран детский профиль с PIN. Пять неверных попыток подряд блокируют проверку на 15 минут по всему аккаунту. Смена детского профиля и устройства счётчик не сбрасывает. Валидный ввод или завершение периода блокировки сбрасывает счётчик. Неудачная попытка сохраняет только счётчик, выбор профиля остаётся прежним. Ошибку счётчика возвращают после коммита, чтобы транзакция её не откатила.
5. **Устройство и вход.** Используется DB backend для сессий Django. Один вход из браузера создаёт под блокировкой аккаунта одну запись `Device` на ключ сессии после повторной проверки `is_active` и неизменности пароля. Данные сессии сохраняются в той же БД до ответа, чтобы запись устройства не осталась без сессии. Вкладки одного браузерного входа используют одно устройство. Имя и тип берутся из безопасной метки браузера, время активности обновляется по входу и запросам, а не по каждому байту. Обработчик авторизованного запроса проверяет совпадение ключа, владельца и отсутствие отзыва устройства. Из списка владелец завершает нужное устройство. Сервис под блокировкой аккаунта выставляет `revoked_at`, удаляет запись DB session и закрывает все плееры устройства в той же транзакции. При отзыве текущего устройства браузер получает переход на вход. Остальные устройства действуют. Просроченные записи Django sessions тоже недействительны, периодическая очистка может убирать старые устройства.
6. **Два вида ограничения.** Блокировка `is_active=False` прекращает вход, отзывает устройства и плееры, записывается в аудит. Подписка продолжает учитывать время своего периода, финансовые данные остаются в истории. `can_post_reviews=False` ограничивает создание и редактирование текста отзыва всеми профилями аккаунта. Вход, оценка без текста и оплаченный просмотр доступны по обычным правилам.

## 4. Подписки и учебная оплата

У подписки один период и история попыток его оплаты. Статусы подписки в интерфейсе — «Ожидает оплаты», «Активна», «Истекла», «Прекращена». Для платежа — «Ожидает подтверждения», «Успешен», «Отклонён», «Возвращён». Новая покупка разрешена только при отсутствии действующего периода. Действующая подписка удовлетворяет `user_id = current_user`, `status = active` и `start_at <= now < end_at`. Команда обработки приводит просроченные записи к `expired`. Даже если команда ещё не отработала, право прекращается при `end_at`. Перед созданием черновика и перед активацией нового периода под блокировкой аккаунта вызвать ту же операцию истечения: если прежняя запись ещё `active`, но `end_at <= now`, перевести её в `expired` и записать уведомление по ключу периода. Только затем проверять наличие действующего периода или записывать новый статус `active`. Так отложенная команда не приводит к конфликту с частичным уникальным ограничением.

### Оформление и повтор

1. Пользователь открывает тариф, вводит код. `billing.services` проверяет доступность тарифа, нормализует код, проверяет его длину 3–30 и алфавит, активность, срок и диапазон скидки. Даты промокода включительны. Одинаковые условия означают тот же тариф, снимок цены, срок, лимит и применённый код со скидкой. `discount = round_half_up(base_price * percent / 100, 2)`, `amount = base_price - discount`. Суммы на клиенте служат для отображения. При неверном коде форма показывает причину и базовую цену, оплату без кода пользователь подтверждает отдельно.
2. GET с расчётом выдаёт подписанный идентификатор попытки с условиями и ожидаемым текущим черновиком и попыткой. При POST сервер проверяет подпись формы, её владельца и активность аккаунта. Под блокировкой сначала возвращает текущее состояние платежа с известным UUID этого владельца без новой записи. Для нового UUID сверяет расчёт с актуальными условиями и наличие действующего периода. Если условия в форме и в открытой попытке совпадают с актуальным расчётом, возвращает существующую попытку и её UUID, даже если форма открылась до создания черновика. Если переиспользовать попытку нельзя, проверяет, изменились ли расчёт, ожидаемый черновик или попытка. Устаревшая форма получает предложение обновить экран без изменений в БД. После отказа новая попытка создаётся по явному действию с новым идентификатором.
3. При смене тарифа или условий оформить результат в одной транзакции. Прежний черновик → `terminated`, его ожидающий платёж → `declined` с кодом замены. Затем создать новый черновик и платёж. Снимки фиксируют имя тарифа, базовую цену, скидку, длительность и лимит плееров. Уже созданная попытка подтверждается по своему снимку, пока она открыта. Оператор имитатора работает с её UUID.
4. Имитатор локален. Экран оплаты показывает только разрешённые учебные результаты, а POST проверяет владельца операции и CSRF. Серверный обработчик имитатора вызывает `confirm_payment(operation_id, result)`. Сначала находит владельца, затем под его блокировкой перечитывает платёж и подписку. Если владелец существует, его экран читает итог завершённой операции по UUID без повторного изменения. При удалённом или заблокированном владельце, закрытом черновике или наличии действующего периода позднее подтверждение не даёт доступа. Удалённому владельцу результат операции не раскрывается. При сбое до коммита попытка остаётся ожидающей, экран позволяет проверить статус. Повтор после коммита возвращает уже записанный результат.
5. Подтверждение ненулевой оплаты создаёт или сохраняет один тестовый способ владельца. Для нулевой суммы локальное подтверждение, активация и запись успешного платежа проходят одной транзакцией. Сохранённый способ при этом не создаётся и не меняется. Кабинет показывает 0,00 ₽ и обычный статус успеха.

### Переходы статусов

| Событие и инициатор | Подписка | Платёж и итог |
| --- | --- | --- |
| Зритель оформляет заказ | Нет черновика → `pending` или используется прежний с теми же условиями | Создаётся `pending` или возвращается ожидающая попытка. |
| Зритель меняет тариф или условия | Прежняя `pending` → `terminated`, новый черновик → `pending` | Прежняя ожидающая попытка → `declined`. Её поздний ответ оставляет оба состояния прежними. |
| Имитатор подтверждает открытую попытку | `pending` → `active`. `start_at = now`, `end_at = start_at + period_days` | `pending` → `succeeded`, присваивается `paid_at`. Запись платежа, периода, аудита и уведомления коммитится целиком. Повтор не пересчитывает дату. |
| Имитатор отклоняет открытую попытку | Остаётся `pending` | `pending` → `declined`, уведомление об отказе. Пользователь может создать новую попытку. |
| Владелец отключает автопродление | `auto_renew=False`, оплаченный период и его конец сохраняются | Без финансового события. Открытый черновик автоматического продления, если он уже появился, закрывается с отклонением ожидающей попытки. |
| Команда обработки или новая покупка после даты окончания | `active` → `expired` | Уведомление с ключом периода и даты окончания создаётся один раз. Команда повторно читает дату под блокировкой. После завершения периода его плееры не участвуют в лимите. |
| Администратор подтверждает полный возврат текущего ненулевого периода | `active` → `terminated`, `ended_at = now`, автопродление выключается, плееры периода закрываются | `succeeded` → `refunded`, присваивается `refunded_at`. Возврат использует UUID исходной операции, меняет её один раз. Неуспех до коммита не прекращает доступ. |
| Владелец или администратор с разрешением прекращает бесплатный период | `active` → `terminated` с `ended_at = now`, плееры закрываются | Платёж остаётся `succeeded`. Сервер отклоняет денежный возврат по сумме 0,00 ₽. |
| Удаление аккаунта | `active` и `pending` → `terminated`, сроки и история сохраняются | Все ожидающие попытки → `declined`. Оплаченные и возвращённые записи сохраняются. |

Проверки и переходы, включая тестовый возврат, выполняются под общей блокировкой аккаунта. При задержке ответа от учебной операции повторно проверяются её UUID и актуальное состояние под блокировкой. Терминальные ответы не перезаписывают друг друга. При одновременной смене тарифа и подтверждении выигрывает первая закоммиченная операция. Если оплата прошла первой, новая покупка блокируется действующим периодом. Если первым закрыли черновик, подтверждение отклонённой попытки не даёт доступа. Частичная уникальность `active` дополнительно защищает от появления второго активного периода. Подтверждение активной подписки и возврат работают через сервис независимо от того, откуда вызваны.

### Учебное автопродление

Команда `process_subscriptions` отмечает завершившиеся периоды, затем при включённом автопродлении может вызвать имитатор по достижении `end_at`. До этой даты оплаченный доступ сохраняется. Новый период оформляется отдельной строкой с `renewal_of`, по действующим условиям тарифа. Применённый при покупке промокод на следующий период не переносится. Начало нового периода — время успешного подтверждения. При паузе между периодами доступа нет.

Под блокировкой выбрать только последний оплаченный период владельца и проверить его флаг, действующий тариф, отсутствие новой покупки и наличие сохранённого способа при положительной цене. Ожидающая попытка продления хранит ссылку на выбранный способ. Удаление способа отклоняет его открытые попытки продления и обнуляет ссылку. Позднее подтверждение проверяет именно выбранный способ, даже если пользователь уже добавил новый. Если при положительной сумме способа оплаты нет, сервис под блокировкой аккаунта выставляет `renewal_requires_retry` у завершившегося периода и создаёт одно уведомление с переходом к привязке. Команда пропускает автопродление помеченного периода, даже если способ уже привязан. Переход периода в `expired` выполняется независимо от отметки. «Привязать тестовый способ» доступно владельцу и после окончания бесплатного периода. После подтверждения формы по POST с CSRF локальный имитатор выдаёт тестовый токен, а сервис под блокировкой аккаунта сохраняет его в `PaymentMethod`. Повтор привязки переиспользует уже сохранённый способ. Привязка не создаёт платёж, черновик или новый период и не запускает продление. Привязка сохраняет отметку. Только явное действие владельца «Повторить продление» может снять её: сервер под той же блокировкой заново проверяет право на продление и валидный способ, создаёт или возвращает открытую попытку и снимает отметку в одной транзакции. При ошибке отметка сохраняется. Пользователь также может оформить новую подписку вручную по обычным правилам. Удаление способа, отказ имитатора и отключение продления до подтверждения не добавляют период. Повтор команды использует тот же черновик и ожидающую попытку по UUID. После окончательного отказа платёж повторяется по явному действию, а старый черновик при необходимости закрывается перед ручной покупкой. Успешно продлённый период наследует включённое автопродление. При позднем ответе проверяются флаг, способ, текущий черновик и отсутствие другого действующего периода.

## 5. Медиа, сеансы и прогресс

### Граница доступа к файлам

Постеры, обложки и трейлеры опубликованных фильмов имеют публичные маршруты. Запись медиа связывает серверный ключ файла с фильмом. Публикация требует хотя бы один жанр, постер, трейлер и валидный MP4 для просмотра. Администратор загружает материалы через форму. Постеры и обложки — JPEG, PNG или WebP до 5 МБ, трейлеры — MP4 до 100 МБ, полные видео — MP4 до 1 ГБ, субтитры — WebVTT до 1 МБ по п. 4.5.4 ТЗ. Лимит проверяется при чтении потока загрузки, MIME сверяется с фактическим содержимым. Pillow читает изображение, для MP4, включая трейлер и каждый вариант фильма, проверяются структура контейнера, положительная длительность и наличие воспроизводимой видеодорожки H.264. Звуковая дорожка необязательна, при её наличии требуется AAC. MP4 без видеодорожки или с другим кодеком отклоняется с объяснением до публикации. Для WebVTT — UTF-8, заголовок и синтаксис меток. Качества одного фильма проверяются на совпадение длительности и временной шкалы. При наличии истории новый файл может заменить основное видео с сохранением длительности. Для другого монтажа создаётся отдельная карточка. Нераспознанный или недоступный файл блокирует публикацию. Имя хранения генерируется сервером. Новый файл записывается под новым ключом до переключения ссылки. Ключ и версия меняются вместе в одной транзакции. Файл по старому ключу не перезаписывается. Старый файл удаляется после коммита, а при открытом чтении или сбое очистку можно повторить по сверке хранилища с БД.

Полные видео и субтитры лежат в закрытой папке вне публичных маршрутов и раздачи статики. Страница плеера получает URL вида `/watch/sessions/<uuid>/media/<id>/<version_id>/` после POST запуска. При входе проверяются аккаунт, DB session и устройство, активный профиль и его возраст, публикация фильма, право подписки и свободное место. На каждом запросе медиа сервер проверяет те же права и что слот уже занят именно действующим сеансом с этим UUID. Материал должен принадлежать тому же фильму. После проверки прав сервер сверяет версию из URL и текущую версию записи. Для устаревшей версии отвечает `410 Gone` без фрагмента файла. Ключ, длина и данные для Range берутся из одной версии. Уже начатый ответ продолжает читать тот же файл или прерывается при ошибке чтения. Подстановка нового файла в старый ответ запрещена. Блокировка аккаунта или коммит отзыва, возврата, смены профиля, закрытия сеанса или снятия публикации делают следующие запросы недоступными. При истечении проверяется само время окончания.

Плеер использует HTML5 `video` с MP4 H.264/AAC, метаданными в начале файла и `preload="metadata"`. Сервер после проверки доступа разбирает один диапазон HTTP Range. Для разрешённого диапазона возвращает `206 Partial Content`, `Accept-Ranges: bytes`, точные `Content-Range` и `Content-Length`, затем читает нужную часть файла с диска. Допускаются формы `start-end`, `start-` и суффикс. Недостижимый диапазон даёт `416` с размером файла. Синтаксически неверный или множественный диапазон получает `400`. HEAD проверяет доступ и возвращает метаданные. Для обычного GET без Range поддерживается потоковый `200` с повторной проверкой права между порциями. Приложение не открывает файлы по пути, переданному клиентом. Защищённые ответы имеют `Cache-Control: private, no-store`. Решение о доступе принимается перед началом выдачи каждого HTTP-ответа, транзакция не держится во время чтения файла. По возможности ограничить размер отдельного ответа Range, начать проверку с 1 МиБ. Если Firefox не продолжит выдачу при ограниченном диапазоне, проверить обычный Range с проверкой прав между порциями длительного ответа. Прекращение открытого ответа в таком варианте проявится как ошибка загрузки. Уже переданные данные и буфер браузера остаются у получателя.

Скачивание — отдельное действие для помеченного фильма. Перед ответом `Content-Disposition: attachment` проверяются действующая подписка, активный профиль, возраст, устройство, публикация и `allow_download`. Скачивание не занимает место плеера. После ошибки пользователь может повторить действие через карточку. Полученный файл проверяется локально.

**Проверка этапа 1.** На одном разрешённом MP4 объёмом 5–20 МБ сделать временную проверку защищённого endpoint. В Firefox открыть ролик, перемотать в непрочитанную область и проверить `206` и заголовки в сетевой панели. Повторить с диапазоном у конца и ошибочным диапазоном. Отозвать право, затем запросить ещё не загруженный диапазон. Ожидается отказ, а прямой путь к файлу не открывается. Зафиксировать работающий размер диапазона или результат порционной проверки. Если оба варианта дают сбой перемотки или продолжают выдавать новые данные после отзыва, способ доставки остаётся риском этапа 1 и решается до основной реализации плеера.

### Что хранится при просмотре

| Уровень | Для чего нужен |
| --- | --- |
| Django session | Подтверждает вход в браузере. По отзыву исчезает право на любые личные запросы. |
| `Device` | Показывает вход в списке, связывает аккаунт и активный профиль. Один вход может иметь несколько вкладок. |
| `PlaybackSession` | Один выданный слот тарифа. Сеанс жив, пока не закрыт и `last_seen_at > now - 120 секунд`, устройство и период действуют. |
| `WatchHistory` | Последняя позиция и отметка завершения пары «профиль — фильм». В кабинете «Продолжить просмотр» выводит доступные незавершённые фильмы с позицией больше нуля и ниже 95 %. |
| `WatchEvent` | Один факт на принятый сеанс. `started_at` записывается при выдаче слота, `completed_at` — при первом достижении порога текущего просмотра. Очистка сеанса обнуляет связь с ним и сохраняет факт. |

### Запуск и изменения позиции

| Действие | Проверка и результат под блокировкой аккаунта |
| --- | --- |
| Старт из карточки или истории | Перечитать устройство и выбранный профиль, подписку и фильм. Посчитать живые сеансы всего аккаунта по текущему периоду. Если место есть, создать `PlaybackSession` и `WatchEvent` в одной транзакции, назначить его записывающим сеансом `WatchHistory`. При заполнении лимита сохранённый прогресс и действующие сеансы сохраняются, экран предлагает открыть устройства. |
| F5, повтор POST с тем же UUID | Вкладка хранит UUID в `sessionStorage`. Для действующего сеанса того же устройства, профиля и фильма ответ возвращает тот же слот, позицию и текущий номер обновления. Сервер сверяет и ключ вкладки. Для закрытого или истёкшего UUID старый POST сообщает о завершении сеанса, явное продолжение получает новый ключ. |
| Закрытие вкладки, тайм-аут и продолжение | Плеер отправляет запрос активности не реже раза в 30 секунд и позицию раз в 15 секунд при воспроизведении, а также при паузе. При отсутствии активности 120 секунд слот сразу исключается из счётчика. Продолжение создаёт новый сеанс и факт запуска, сохраняя позицию и `is_completed`. |
| «Начать заново» | POST передаёт UUID заменяемого сеанса, если он есть, и новый UUID. Сначала обработать повтор нового UUID. Проверить, что старый сеанс соответствует этому устройству, профилю, фильму и исходной вкладке, а ожидаемый записывающий сеанс истории не успел смениться. Закрыть только подтверждённый сеанс, затем проверить лимит, создать новый слот и факт, обнулить позицию и отметку завершения. При отказе откатываются и закрытие старого, и сброс. |
| Позиция, перемотка и 95 % | Принять целые секунды в пределах длительности и растущий `seq` для сеанса. После первого достижения `position * 100 >= duration * 95` поставить `is_completed` и один раз заполнить `completed_at` факта этого сеанса в общей транзакции. Перемотка назад меняет позицию, отметка сохраняется. Повтор того же `seq`, устаревший или закрытый сеанс не переписывают прогресс. |
| Одновременный плеер того же профиля и фильма | Если тариф допускает второй слот, новый сеанс становится `writer_session`. Старый может смотреть до закрытия, но получает статус «Позиция сохраняется в другом плеере». Прогресс и завершение меняет только текущий записывающий сеанс. При явном продолжении новый запуск снова назначает владельца записи. |
| Отзыв устройства и очистка | Отзыв закрывает все его слоты в транзакции удаления Django session. Следующий Range отклоняется, другое устройство может сразу занять место. Команда очистки закрытых и давно истёкших сеансов сохраняет личную позицию, обнуляет `writer_session` и `WatchEvent.session` при удалении соответствующего сеанса. |

Для различения вкладок при старте используется случайный ключ вкладки из `sessionStorage`, связан с сеансом на сервере. Ссылки в новую вкладку открываются без доступа к исходному окну. Для обнаружения скопированного состояния две открытые вкладки сверяют ключ через `BroadcastChannel`. Новая получает собственный ключ до независимого запуска. При F5 прежняя страница уже завершилась, поэтому ключ сохраняется. UUID и ключ вкладки не заменяют проверку DB session, владельца, профиля и фильма. Закрытые сеансы хранятся не менее суток после закрытия или тайм-аута. Для ещё неизвестного UUID сервер принимает только подписанное намерение запуска сроком до суток. Действующий UUID можно возобновить после проверки привязки к вкладке и входу. Просроченное намерение после очистки сеанса не создаст новый запуск.

При смене качества воспроизведение остаётся в том же сеансе, позиция переносится после загрузки метаданных. Субтитры подключаются как WebVTT к защищённому URL. Ошибка файла оставляет сохранённую позицию. По действию «Повторить» сервер проверяет текущий сеанс и право доступа, возвращает URL действующей версии выбранного качества. После загрузки метаданных плеер восстанавливает сохранённую позицию. Повтор в действующем сеансе не создаёт новый слот и факт запуска. Достижение 95 % проверяется по отправленной позиции. Это метрика учебного плеера, которая включает перемотку и служит для истории и отчёта.



## 6. Каталог, избранное, отзывы и рекомендации

`catalog.queries` формирует общую выборку опубликованных и допустимых по возрасту фильмов. Форма GET проверяет строку поиска до 100 символов, жанры из действующего справочника, год от 1888 до текущего года плюс один, рейтинг от 1 до 5 и допустимую сортировку. Поиск по подстроке названия регистронезависимый. Достаточно одного из выбранных жанров, остальные фильтры применяются совместно. Для жанров использовать `Exists`, чтобы фильмы и оценки не дублировались. Смена параметров сбрасывает страницу. Сортировка по дате публикации, названию или рейтингу завершается стабильным ключом `id`. Избранное добавляется и удаляется через отдельные POST с проверкой профиля, повтор соответствует уже достигнутому состоянию.

`Review` содержит одну текущую оценку и при наличии один текст. При подсчёте берутся записи с пустым текстом и записи с текстом в статусе `published`. Единая ORM-выборка вычисляет среднее и число учтённых оценок, округляет среднее до десятых. Карточка, сортировка и минимальный рейтинг используют одно и то же округлённое значение. Без учтённых оценок среднее `NULL`, карточка показывает «Нет оценок», при сортировке по рейтингу такие фильмы идут в конце, при фильтрации по минимуму исключаются.

| Действие | Состояние записи и влияние на рейтинг |
| --- | --- |
| Сохранить или изменить оценку 1–5 | Если текста нет, статус пуст и оценка сразу учитывается. При существующем тексте отдельная форма оценки сохраняет текст и статус, применяет обычное правило учёта. |
| Добавить или явно изменить текст | Сервер проверяет `User.can_post_reviews` у владельца и длину текста после обрезки 10–2000 символов. Запись → `pending`, прежняя причина очищается, оценка исключается. Это относится и к опубликованному тексту. |
| Опубликовать или отклонить | Для `pending` модератор выбирает `published` или `rejected`. При отклонении обязательна причина 5–500 символов. Публикация возвращает оценку в рейтинг, отклонение её исключает. |
| Снять с публикации | `published` → `removed` с причиной 5–500 символов. Текст исчезает из карточки, оценка исключается. |
| Удалить свой текст | Отдельный POST очищает текст, статус, дату отправки и причину, оценка сохраняется и снова учитывается. Действие доступно при ограничении на публикацию. |
| Ограничить автора | Модератор меняет `User.can_post_reviews`. Действующие отзывы и очередь сохраняют свои состояния. Для скрытия конкретного текста используется снятие с публикации. |
| Удалить профиль | Каскад удаляет оценки, отзывы и избранное. Среднее и число голосов при следующем чтении считаются по оставшимся записям. |

Редактирование и действия очереди передают `version`, сервер сверяет версию и статус под блокировкой владельца и строки отзыва. Устаревшему экрану предлагается обновить запись. Это исключает публикацию версии, которую модератор не видел. Изменение и служебное решение увеличивают версию, повтор POST с прежней версией не создаёт нового решения и уведомления. Причина и статус видны автору в кабинете. На публичной карточке выводятся только опубликованные тексты. В аудит попадают тип решения и безопасные ссылки, пользовательский текст и причина модерации хранятся в самой записи отзыва.

Для подписчика рекомендации строятся по жанрам из истории и избранного активного профиля. Один балл за каждый совпавший жанр, затем сортировка по рейтингу, новизне и `id`. Фильтруются опубликованные и доступные по возрасту фильмы, просмотренные исключаются. Если нет истории интересов или совпадений, показать доступные новинки с теми же исключениями. На этапе 2 каталог готов без рейтинговых данных, на этапе 6 к нему подключается общая выборка.

## 7. Удаление, поддержка и аудит

### Удаление аккаунта

`config.workflows.delete_account()` вызывается кабинетом после проверки текущего пароля или Admin после подтверждения и проверки разрешения. Операция идёт под блокировкой целевого аккаунта в одной транзакции. Сначала она отзывает все устройства и DB sessions, закрывает плееры, прекращает активный доступ и черновики, отклоняет незавершённую оплату. Затем очищает персональные поля служебных записей, удаляет аккаунт. База или ORM обнуляет и каскадно удаляет связи по таблице моделей. Если любое изменение до коммита не удалось, аккаунт, доступ и связанные данные сохраняют прежнее состояние. Повтор после коммита не выполняет операции заново. Запоздалое подтверждение и запрос прогресса отвергаются после повторной проверки владельца.

| Данные | Результат |
| --- | --- |
| Аккаунт и личная часть | Удаляются логин, email, имя, телефон, хеши, профили, устройства, сеансы, личная история, оценки, отзывы, избранное, способы оплаты и личные уведомления с настройками. Строки ограничений для текущих идентификаторов удаляются по ключам, оставшиеся ограничители IP и старых идентификаторов живут до технического срока истечения. |
| Подписки и платежи | `Subscription.user` обнуляется после прекращения действующих и ожидающих периодов. `Payment.subscription` остаётся обязательным. Сохраняются снимок тарифа, суммы, даты, статусы и случайный идентификатор тестовой операции. Контактные данные и токены способа в исторические строки не записываются. |
| Факты просмотра | `WatchEvent.profile` и `WatchEvent.session` обнуляются. Фильм, время запуска и время завершения остаются. Сведения об устройстве, аккаунте и позиции в факте отсутствуют. |
| Поддержка и аудит | Обнуляются соответствующие ссылки на владельца обращения, автора сообщения, исполнителя и затронутый аккаунт. Сохраняются служебные даты, тип автора, результат, статусы и безопасная часть ответов. |

### Обращения и очистка переписки

Зритель отправляет тему 5–100 и сообщение 10–2000 символов. В одной транзакции создаются обращение со статусом «Новое» и первое сообщение. Кабинет показывает номер и переписку только владельцу. Администратор видит очередь и переводит обращение «Новое → В работе → Закрыто», может ответить и закрыть его в одном действии. На закрытии требуется хотя бы один ответ. Удалённый владелец оставляет обращение в служебной истории. Ответ и уведомление записываются вместе, повтор одной формы ответа защищается выданным для неё ключом. Ответ блокирует аккаунты автора и владельца, затем строку обращения. Очистка блокирует целевой аккаунт, затем затронутые обращения. Перед записью сервис перечитывает автора, владельца и статус. Ответ после удаления владельца к личной переписке не добавляется.

У обращения есть отдельный `owner`, а у сообщения — `author` и `author_kind`. Ответ администратора состоит из выбранной фиксированной фразы без подстановок клиента и необязательного свободного текста. Например, «Обращение рассмотрено» и «Для решения требуется повторить действие». Кабинет показывает обе части до удаления. При удалении клиента тема и свободные тексты клиента и администратора в его обращениях целиком очищаются, включая возможные цитаты. Фраза из справочника, даты и статус сохраняются. При удалении администратора в его ответах тоже остаётся фиксированная фраза, ссылка на автора и свободное дополнение удаляются. Это можно проверить по отсутствию свободного текста и идентификаторов в затронутых строках. Отдельный поиск произвольных упоминаний человека в чужих обращениях этой процедурой не покрывается.

### Журнал

Аудит записывает дату, исполнителя, тип действия, объект и код результата. Обязательные события — смена ролей, блокировка, публикация и снятие фильма, решения модерации, подтверждение оплаты, возврат и восстановление БД. Для персональных объектов используется nullable-ссылка на затронутый аккаунт. Логин, телефон, почта, свободный текст, пароль, PIN и токены не пишутся в журнал. Переписка и технические логи не копируются в аудит. Администратор фильтрует записи по периоду, действию и результату через представление только для чтения. Доступ к журналу — отдельное разрешение. Сохранение при удалении опирается на структурированные поля, которые отсутствуют в экспортируемых отчётах.

## 8. Отчёты, уведомления и восстановление

| Отчёт | Источник и границы |
| --- | --- |
| Подписки | `Payment.paid_at` определяет число подтверждённых операций и начисления, включая те, что были позже возвращены. `refunded_at` отдельно определяет число и суммы возвратов за период. Итог — начисления минус возвраты периода. Успех на 0,00 ₽ увеличивает число операций на один и сумму на ноль. Возврат в другом периоде учитывается по дате возврата. |
| Просмотры | Группировка `WatchEvent` по фильму. Запуск учитывается по `started_at`, завершение по `completed_at`. Если события попали в разные периоды, каждое считается в своём. Удаление устройства, профиля и аккаунта не меняет итоги. |

Форма валидирует начало и конец. Включительные местные календарные даты преобразуются в полуоткрытый интервал от полуночи первой даты до полуночи суток после конечной. Просмотр и выгрузка используют одну выборку. Пустой период даёт нулевые итоги. CSV в UTF-8 и XLSX содержат период, заголовки и строки отчёта. Названия выводятся как текст и обезвреживаются для табличных формул. Контактов и реквизитов в выгрузке нет.

По результатам оплаты, возврата, окончания периода, ответу поддержки и решению модерации создаётся уведомление кабинета. Ключ строится по типу события и UUID операции, номеру сообщения, версии решения или паре «подписка — конец периода». Повтор фоновой команды или ответа имитатора не увеличивает число уведомлений. Пользователь отмечает свои уведомления прочитанными. Настройка рассылок влияет на тестовую необязательную рассылку администратора в центр уведомлений. Перед созданием запись согласия проверяется повторно под блокировкой получателя, для одной рассылки используется общий ключ, уникальный в пределах получателя. Служебные сообщения и одноразовая ссылка восстановления не зависят от согласия на рассылку. Восстановление использует файловый почтовый backend с доступом только для оператора учебного стенда.

Копирование запускается из Admin по POST с отдельным разрешением. Команда использует `pg_dump --format=custom` с настроенным подключением и фиксированным каталогом вне веб-доступа. Имя включает дату, время и уникальный суффикс. Сначала пишется временный файл. После успешного завершения и проверки читаемости списка архива через `pg_restore --list` файл атомарно переименовывается, в `BackupRun` появляется «Готова». Сбой даёт «Ошибка», код причины и время окончания. Если процесс оборвался до записи результата, следующий запуск или оператор сверяет запись с архивом и отмечает прерванную попытку. Временные файлы не считаются готовыми копиями. Копия PostgreSQL содержит данные и метаданные файлов. Для проверки стенда нужен тот же набор файлов из отдельно сохранённой демонстрационной коллекции. Учебные копии и тестовая почта используются только с демонстрационными данными.

По п. 4.2.2 ТЗ провести два независимых испытания. Остановить приложение при исправной БД и замерить время от обнаружения остановки до успешного открытия контрольной страницы, цель — до 5 минут. Для сценария повреждения БД создать отдельную пустую тестовую базу с отличающимся именем, восстановить архив `pg_restore` с остановкой на ошибке и запустить приложение с отдельной конфигурацией. Цель — до 30 минут от обнаружения сбоя до подтверждённой работоспособности. После восстановления проверить вход, каталог, связь «аккаунт → подписка → платёж» и право на тестовое видео. Зафиксировать дату копии, начала и окончания, проверки и фактическое время для приложения Б, записать результат операции восстановления в аудит после появления доступной БД. Проверка списка архива служит проверкой файла, а испытание восстановления подтверждает данные и рабочий сценарий.

## 9. Интерфейс и дизайн

### Визуальное направление

Absolute Cinema — публичное название сервиса. Шаблоны и служебная панель получают его из настройки Django `SITE_NAME`.

Тёмный фон `#111827` задаёт сцену. Чуть более светлые поверхности отделяют фильтры, формы, блоки кабинета и служебные таблицы. Основной текст `#F9FAFB`, вторичный — холодный серый с проверенным контрастом. Акцент `#7C3AED` — заливка главной кнопки и выделение выбранных элементов. Для текста ссылок и фокуса использовать более светлые оттенки фиолетового. Зелёный, жёлтый и красный всегда сопровождаются словом статуса или понятным значком. Типографика — системный стек `system-ui, Segoe UI, sans-serif` с поддержкой кириллицы, основная шкала 16/20/28/40 px. Названия и суммы выделяются кеглем и весом, метаданные читаются одной строкой или короткими группами.

На главной ведёт один крупный кадр с заголовком и действием. Новинки раскрываются полкой постеров ниже. В каталоге внимание делится между поиском, результатами и чёткой сеткой, все постеры имеют соотношение 2:3. В карточке сначала название и возможность просмотра, затем подборка метаданных, описание и отзывы. Фиолетовая кнопка одна на основной блок. Композиция строится вокруг собственных кадров и оформления стенда.

Подписи полей видны до и после ввода, ошибки привязаны к полям, динамические статусы сообщаются через подходящую область оповещения. Текст поверх изображения получает затемняющую подложку. ### Состояния и демонстрационные материалы

| Состояние | Что видит пользователь и что может сделать |
| --- | --- |

| Платёж отклонён или результат ещё уточняется | Конкретный статус и действие «Повторить оплату» при отказе, «Проверить статус» при ожидании. |
| Загрузка или сбой видео | Показать загрузку, при ошибке — понятное сообщение и «Повторить». Позиция восстанавливается с сервера. Если право отозвано, вместо повтора показать причину и доступное действие. |
| Пустые избранное, история или рекомендации | Для пустых личных списков — ссылка в каталог, для рекомендаций — подборка новинок при наличии подходящих фильмов. |

Для стенда подготовить 6–8 оригинальных или разрешённых к использованию постеров 2:3, 1–2 широких кадра для баннера, несколько коротких трейлеров и роликов. Для каждого файла сохранить источник или основание использования при подготовке данных. Согласовать цветокоррекцию, насыщенность и размещение названий в серии. Постеры выдавать в двух размерах по ширине, за пределами первого экрана загружать лениво. Плеер подгружает метаданные, трейлеры запускаются по действию пользователя. Для скачивания использовать 5–20 МБ, показать хотя бы один ролик с двумя качествами и одной дорожкой WebVTT. Материалы держать локально, чтобы демонстрация не зависела от внешней сети.

**Первыми проработать четыре экрана.**

1. **Главная.** В верхней части широкий кадр с затемнением в зоне заголовка, основной переход в карточку. В первом же экране виден край полки новинок. На 360 px заголовок и действие размещаются под кадром.
2. **Каталог.** Поиск и счётчик над результатами, на большом экране слева компактные фильтры, справа ровная сетка постеров. На мобильном фильтры открываются отдельной панелью, сетка занимает всю ширину.
3. **Карточка фильма.** Постер слева, название, возраст, жанр, рейтинг и основное действие справа. Трейлер и краткое описание рядом с зоной выбора, отзывы ниже. На узком экране название и основное действие остаются в верхней части композиции.
4. **Плеер.** Кадр видео в центре с нейтральным тёмным окружением. Над ним короткий заголовок и возврат, под ним позиция, варианты и начало заново. Ошибка занимает область рядом с видео, сохраняет выход к карточке и подходящее действие.



## 10. Структура проекта и первая миграция

```text
OnlineCinema/
  ARCHITECTURE.md
  manage.py
  requirements.txt
  config/
    settings.py
    urls.py
    wsgi.py
    workflows.py
  accounts/
  catalog/
  billing/
  viewing/
  operations/
  templates/
    base.html
    components/
    accounts/
    catalog/
    billing/
    viewing/
    operations/
    moderation/
    admin/
  static/
    css/
    js/
    images/
```

У каждого приложения свои `models.py`, `migrations/` и при необходимости `forms.py`, `views.py`, `urls.py`, `admin.py`, `queries.py`, `services/`. Команды биллинга и резервного копирования лежат в `management/commands/` своих приложений. `config.settings` читает параметры БД, секреты и пути к файлам из окружения. Полные видео, субтитры, рабочие копии БД и временная почта лежат в заданных окружением отдельных каталогах вне `static/` и прямого веб-доступа. Django-раздача статики на локальной проверке не получает маршрута к закрытому хранилищу.

**До первой миграции закрепить следующие решения.**

1. PostgreSQL на всех средах. `accounts.User` объявляется в `accounts/0001_initial.py`. Настройки `AUTH_USER_MODEL`, backend входа и DB sessions выбираются до первого `migrate`. В начальной модели обязательны логин и email, уникальности `Lower`, стандартные поля прав Django и `can_post_reviews`. Ссылки других приложений используют `settings.AUTH_USER_MODEL`. Группы и разрешения назначаются командой подготовки стенда после создания таблиц.
2. Роли хранятся в группах, подписчик вычисляется по времени. Хеш PIN принадлежит детскому профилю, счётчик попыток — аккаунту, а активный профиль — устройству. Часовой пояс отчётов — Москва, сохраняемые даты — с часовым поясом.
3. Один период подписки — одна строка, платёж всегда связан с ней. Исторический владелец может быть `NULL`, действующий — нет. Защита двух активных подписок состоит из блокировки аккаунта, проверки времени и частичной уникальности.
4. Личный прогресс и обезличиваемый факт запуска хранятся в разных таблицах. Отдельный сеанс плеера лимитирует выдачу. Уникальные пары «профиль — фильм» и nullable-связи фактов задаются в миграциях до применения данных.
5. Дальнейшие миграции идут по зависимостям. Аккаунты предшествуют своим FK, каталог и тарифы — подпискам и просмотрам. Тариф доступен на этапе 2 отдельной миграцией биллинга, остальные его модели добавляются на этапе 4. Минимальные модели аудита и уведомлений появляются с первыми событиями, экраны журнала и уведомлений — на этапе 7.

### Риски и вопросы, которые могут изменить решение

| Вопрос | Практическое последствие и следующий шаг |
| --- | --- |
| Закрытая выдача MP4 и перемотка в Firefox | Размер диапазона и способ прерывания длинного ответа зависят от фактического поведения плеера. Контрольное видео и отзыв доступа проверяются на этапе 1. |
| Доступность стека и время восстановления | Установленные файлы Python и PostgreSQL не подтверждают совместный запуск. Этап 1 проверяет зависимости, чистые миграции и подключение. Целевые 5 и 30 минут проверяются только испытаниями на этапе 8. |
| Состав демонстрационной медиаколлекции | Для проверки скачивания и разных вариантов нужны разрешённые исходники, закодированные заранее. До этапа 2 выбрать набор и зафиксировать источники. Если встроенной проверки контейнера не хватит для фактических файлов, необходимость отдельного инструмента согласовать после проверки. |

Перед первой миграцией проверить, что `Profile.pin_hash` принимает полный хеш, а `User` хранит только общий счётчик попыток и срок блокировки. Для устройства предусмотрены ссылки на активный и исходный защищённый профили. После удаления исходного профиля с другого устройства действует подтверждение владельцем, описанное в разделе 3.

Для остальных неоднозначностей в документе заданы правила по умолчанию. Выбор пользователя понадобится, если на защите нужен иной объём одной из двух операций ниже.

- **Автопродление и возврат.** В документе продление выполняется по текущему тарифу без переноса промокода при наступлении конца периода, а возврат сделан для текущего оплаченного периода, как в ТЗ. Для заранее оплаченного будущего периода, повторной скидки или возврата за прошлые периоды понадобятся другие правила дат и переходов. Подтвердить расширение перед изменением биллинга.
- **Хранение ответа поддержки.** Базовый вариант сохраняет безопасную часть ответа. Ответ сохраняется как фиксированная фраза, дата и статус. Свободное дополнение очищается целиком. Проверка удаления описана в плане и в разделе 12.

### Первый сквозной сценарий

Гость открывает каталог, фильтрует подборку, смотрит трейлер опубликованного фильма 12+, регистрируется, входит со взрослым профилем, выбирает тариф на один сеанс и оплачивает через имитатор. Из карточки запускает полное видео, доходит до 30 % и ставит на паузу. F5 сохраняет тот же запуск. После тайм-аута пользователь открывает «Продолжить просмотр» и видит прежнюю позицию. Параллельный плеер на втором устройстве получает отказ. После возврата администратором новый диапазон видео больше не выдаётся. Это первый сквозной результат этапа 5.

Минимальные данные для основного сценария — один опубликованный фильм 12+ с жанром, постером, трейлером и разрешённым полным MP4, один активный тариф на 7 суток с одним слотом, один тестовый зритель после регистрации, два изолированных входа этого зрителя в Firefox и служебный администратор. Для негативного прогона добавить черновик и фильм 16+, детский профиль, тариф с другими условиями, истёкший промокод и код 100 %, отдельные записи для модератора и пользователя с ограничением на отзывы.
